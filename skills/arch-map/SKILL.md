# arch-map — アーキテクチャを「クリックできる図」にする

成果物はプロジェクト内の 2 ファイルだけ。

- `docs/arch-map/arch-data.js` … 図の中身（JSON）。**書くのはこれだけ。**
- `docs/arch-map/index.html` … 見た目のテンプレート。仕上げのスクリプトが自動で置く。**読まない・手で書かない。**

今回の引数: 「$ARGUMENTS」（`plan` = 計画だけ / `built` = 実装だけ / 空 = 自動）

## 1. モードを決める

- `docs/arch-map/arch-data.js` がある → **更新モード**（§3）。ただし「作り直して」と頼まれたときは、§2 の新規モードで描き直す（役割が残る箱の `id` と `name` は引き継ぐ。`name` は利用者が書き換えたものかもしれない）
- ない → **新規モード**（§2）。書き始める前に `${CLAUDE_SKILL_DIR}/reference/schema.md` を読む
- 対象: 引数があればその図だけ。空なら、コードがあれば built、計画の情報があれば plan（両方あれば両方）

## 2. 新規モード

### 2a. 実装（built）を読む — 事実から機能を拾う

1. 全体像: `git ls-files | head -300`（git でなければ `find . -type f` で `.git` `node_modules` `dist` `build` `.venv` を除外）と、フォルダごとのファイル数を見る
2. 読むのは構成がわかるファイルだけ: マニフェスト（package.json, pyproject.toml, go.mod, Cargo.toml など）、エントリポイント、ルーティング、DB スキーマ・マイグレーション、docker-compose、`.env.example`（キー名だけ）、README
3. **実際の境界**をつかむ: どこで動くか（ブラウザ・サーバー・Worker・CLI・バッチ・スマホ）、何がまとめてデプロイされるか、パッケージ／サービスの分かれ目、データの置き場所。設定ファイル（`wrangler.toml` `vercel.json` `Dockerfile` `docker-compose.yml` `package.json` の workspaces や bin など）が手がかり
4. **機能を事実から拾う**: コードに実在する機能を、漏れなく洗い出す。数は決めない。ここで拾うのは「何ができるか」で、箱の単位は §4 の「箱は機能」で決める（操作 1 つずつを箱にするわけではない）
   - 出どころ: 画面の操作（ボタン・メニュー・ジェスチャー・キーボードショートカット・シートやダイアログ・設定項目）、入口（ルーティング・コマンド・URL スキーム・ファイルを開く・共有から受け取る・通知・ウィジェット。アプリの設定ファイルやアプリ拡張も見る）、裏で動く処理（同期・自動保存・起動時の復元・タイマー・アプリの状態の変化・OS からの通知）、外とのやりとり（取り込み・書き出し・共有・課金・外部 API）
   - grep で取りこぼしを確かめる: UI のイベント処理（`Button(` `.onTapGesture` `@IBAction` `onClick` `addEventListener` `.keyboardShortcut` メニュー項目 など、その言語・フレームワークの書き方）、ルート定義、コマンド定義、一覧データからまとめて作る操作（enum を回して並べるショートカットやスライダーなど）、通知とタイマー（`NotificationCenter` `Timer` `setInterval` `scenePhase` など）
   - 拾った機能を、作業用の表に「機能 / きっかけ（どの操作で始まるか）/ それを担う型やファイル」で書き出す（置き場所は `docs/arch-map/` ではなく、プロジェクトの外の一時フォルダ）。担う型やファイルが同じ機能は、§4 のとおり 1 つの箱になる。表のどの機能も、どれかの箱が担っていることを確かめる
5. **入力から最後の出力まで流れを追う**: 主な使い方（画面からの操作、CLI、定期実行、Webhook など入口ごと）について、入口 → 受付・検証 → 処理の各段階 → 保存 → 結果の組み立て → 返却 → **最後の出力**（画面に出る結果、ターミナル出力、ファイル、レポート、通知、外部への応答など）までをたどる。定期実行や Webhook など、本番で動く裏方の流れも同じようにたどる。各機能が初めて動く順番が `step` になり、同じ機能に戻るところは戻る線になる
6. **外部サービスを洗い出す**: 依存パッケージ・import・通信先のドメイン・`.env.example` のキー名から、使っている API・SaaS・マネージドな DB やストレージ・ホスティングを特定する
7. 機能を事実から拾うため、ソースはすべてのファイルに目を通す。全行を読む必要はなく、ファイルごとに「どんな型（クラス・構造体・モジュール）があり、何をし、どの型を呼ぶか」が分かればよい
   - 100 ファイルを超えるなら、領域（フォルダやモジュール）ごとに Explore サブエージェントを並列で起動する（目安は 1 体 30〜50 ファイル）。返す形式を指定する: 型やファイルの単位ごとに「単位（型名・ファイル）｜何をするか（ひとこと）｜できる操作やきっかけ（ボタン・メニュー・ショートカット・OS からの通知など）｜呼び出している単位（型名と関数名、何を頼むか）」の 1 行と、外部サービス（サービス名と環境変数の名前）。呼び出し先が型名で返ってくるので、そのまま §4 の箱と線になる
   - 3,000 行を超えるファイルは、型・関数の一覧（`MARK` やクラス・関数の宣言）から構成をつかみ、関係する範囲だけ読む
   - テストコードは、機能の数え漏れを探す照合に使う
8. 本番の箱にしないもの: デバッグビルドだけで動くものは、実装用の道具として描く（§4）。どこからも呼ばれていないコードは箱にせず、近い箱の `built.note` に書く
9. 進み具合（progress）や不具合（issue）は、TODO・未実装の関数・失敗中のテストなど**根拠があるときだけ**書き、根拠を `built.note` に残す

### 2b. 計画（plan）を読む

- 情報源: この会話で決まった計画、plan モードの計画ファイル、`PLAN*.md` `SPEC*.md` `docs/**/*.md` `README.md` `CLAUDE.md`、`要件` `設計` を含むファイル
- 計画書から当然必要になる箱（「メール+パスワード認証」とあればログイン画面など）は plan に置いてよい。そのときは `plan.note` に「計画書には明記なし」と書く。置くグループが決まらない機能は、いちばん近いグループに置いて note に書く
- 計画書で見送り・中止になったものは plan に入れず、`log` に 1 行残す
- 計画の情報が何もない場合、引数が `plan` のときだけ「何を作る予定か」を 1 回質問する。それ以外は計画を空のままにする（**コードから計画をでっち上げない**）

### 2c. データを書く

§4 のルールで `docs/arch-map/arch-data.js` を Write する。計画と実装の両方を書くときは、同じものに同じ id を使う。箱が多くて一度に書けなければ、プロジェクトの外の一時フォルダに生成用のスクリプトを書いて出力してよい（生成用のスクリプトはプロジェクトに残さない）。

## 3. 更新モード（変わったところだけ）

1. `docs/arch-map/arch-data.js` を Read する（これ自体が形式の見本。schema.md は迷ったときだけ読む）
2. 前回からの変化を調べる:
   - `git rev-parse --is-inside-work-tree` で git か確かめる。git で `project.commit` があれば `git diff --name-status <commit>` と `git status --porcelain`
   - git でないときだけ `find . -newer docs/arch-map/arch-data.js -type f -not -path './.git/*' -not -path '*/node_modules/*'`
   - `docs/arch-map/` 自体の変更は無視する
   - 計画については、この会話で計画が変わったか、計画ファイルが変わったかを見る
   - 変化が見つからなくても終わらず、先に §5 を実行して ⚠ を確かめる（手順 5）
3. 変わったファイルに関係する箱と線だけを確かめ、**Edit で該当箇所だけ直す**（ファイル全体を書き直さない）
   - 箱の `name` と `project.name` は、利用者が図の右パネルで書き換えていることがある。今ある名前は、その箱の役割が変わったときだけ直す（描き直すときも、同じ id の箱は今の名前を引き継ぐ）
   - 新しい機能 → 計画にあった機能なら、その箱に `built` を足す（id を新しく作らない）。計画にない機能なら `built` だけの箱を足し、`built.note` に「計画書にはない」と書く
   - 進んだ → `progress` を上げる。完成したら `progress` を消す。直った → `issue` を消す
   - コードからなくなった機能 → `built` を消す。計画から外れた機能 → `plan` を消す
   - plan も built もなくなった箱は箱ごと消し、その箱につながる線も消す。それで役目がなくなった箱（その機能専用の外部サービスなど）も同じように扱う
   - 計画の中身が変わった → `plan` を直す
   - 動く場所やデプロイ単位が増えた・変わった → `groups` を直す。外部サービスを足した・替えた → `service` を直す
   - 最後に `project.summary` と `glossary` が古くなっていないか確かめる
4. 意味のある変化ごとに `log` の末尾へ 1 行足す（`view` は plan / built / both。`date` は省略すればスクリプトが今日の日付を入れる）
5. コードにも計画にも変化がなくても §5 を実行し、⚠ に描き方の不足（step がない、最後の出力がない、開発用の道具が組み込みに混ざっている など）が出たら、このルール（§4）に沿って直す。step がない古い図は、§2a の 4・5 のとおり機能を拾い直し、入口から最後の出力まで流れを追い直して描き直す（ルールに合わない箱・線は消し、足りないものは足す）。⚠ もなければ「変更なし」と報告する
6. 同じ箱を複数の段に置いていた古い図（`step` が配列）は、スクリプトが最初の段だけに直す（「形式:」の行が出る）。そのときは §4 のとおり、段の番号と、もう一度その機能に戻るところの戻る線を見直す。いくつもの機能を 1 つにまとめた箱（「パネル類」など）があれば、§2a の 4 のとおり事実に合わせて分ける

## 4. データを書くときのルール（初心者向け）

- **組み込みと実装用の道具を分けて、両方描く**
  - 組み込み: 本番のサービスの中で動く部品（画面・サーバー・処理・データ・外部サービス）。起きる順の流れ（`step`）で描く
  - 実装用の道具: サービスを作る・確かめる・調整するために使っているもの（ビルド、画像やデータの準備、評価・調整のスクリプト、確認用の CLI、ローカル用のサーバーなど）。サービスづくりに使われているなら描く。`"tool": true` のグループに入れると、流れの図の後ろ（横の流れなら右端、縦の流れなら下）の「⚒ 実装用の道具」の区画に分けて描かれる。`step` は付けない
  - 道具の箱は、使い道ごと（ビルド・テスト・計測・ログの解析・素材の準備・アプリ内の診断機能など）に 1 つにまとめてよい。中身のスクリプトやファイルは `built.files` と `detail` に書く
  - 道具の線は、それが作る・試す・調整する組み込みの箱へ引く（「公開用にまとめる」「採点の基準を調整する」「判定を試す」）。1 つの道具の線は主な相手 1〜2 本に絞る。道具には最後の出力の箱を付けない
  - 道具のグループは `groups` の最後に書く。開発者（人）の箱は描かない。道具の区画が開発用であることは図で分かる
  - そのアプリ自体が CLI ツールや開発者向けの製品なら、そのコマンドは組み込みとして流れに描く
- **箱は機能**。コードの中で独立した単位（画面・パネル・シート、サービス・マネージャー・エンジン・ストアなどの型やモジュール、データの置き場所、外部サービス、裏で動く処理）が担う機能を、1 つの単位につき 1 つの箱にする。ラベル（`name`）は、その単位が何をするかを表す
  - 数は決めない。コードにある単位はすべて描く（省くと図の意味がなくなる）
  - 別々の単位を 1 つの箱にまとめない（「パネル類」「エンジン」のような箱は作らず、レイヤーパネル・カラーパレット・筆圧フィルタ・手ブレ補正のように分ける）。1 つの単位を複数の箱に分けない
  - 1 つの大きな型でも、機能ごとにファイルや拡張（`Renderer+Fill` `Renderer+Selection` など）が分かれていれば、それぞれを箱にする
  - ただし、画面の見た目を分けただけのファイル（上辺バー・ボタン列などのレイアウト）と、1 つの画面やシートの中のタブ・区画は、その画面の箱に含めて `detail` に区画を書く。別の箱にするのは、利用者から見て別のことができる単位だけ
  - 1 つのファイルに型がいくつあっても、1 つの機能のための部品なら 1 つの箱にする
  - **箱にしないもの**（その単位の箱の `detail` や `built.note`、線の `label` に書く）
    - 単位の中の操作 1 つずつ（ボタン・メニュー項目・ショートカット・設定項目）。「レイヤーを追加する」のように線の `label` に書くか、`detail` に並べる
    - 単位の中の処理の段階・係数・閾値・旧版との互換処理などの細部
    - データの種類や見本 1 つずつ（ブラシの種類、用紙の種類、テンプレートなど）。それを扱う単位の箱にまとめる
    - 小さな共通部品（スライダー・プルダウン・確認ダイアログなどの UI 部品、形式の変換、名前の検証、ログの書き込みなどの補助）。使う側の箱に含める
    - OS が出す画面や部品（共有シート・写真の選択・カメラの画面など）。それを呼ぶ箱の `detail` に書く。データが端末やアプリの外へ出るもの（iCloud・外部 API など）は箱にして `service` を書く
  - 同じ名前の箱を作らない（名前で区別できるようにする）
- **図は起きる順に流れる**（横長の画面では左から右、縦長の画面では上から下。見る人が切り替えられる）。各箱に `step` を **1 つ** 付ける
  - `step` は、人の操作を 1 として、その機能が初めて動く順番。主な使い方の流れの順に番号を振る（例: 1 利用者 → 2 判定画面 → 3 受付窓口 → 4 合言葉の門 → 5 判定の司令塔 → 6 判断AI → 7 判定結果の表示）
  - 脇の機能（設定・書き出し・管理画面など）は、それを呼び出す箱の次の step に置く
  - 箱が多く、主な使い方の順番だけでは決めきれないときは、呼び出しの深さで決める: 人 = 1、人が直接操作する箱 = 2、そこから頼まれる箱 = 3 … とし、いちばん浅い呼ばれ方で数える（結果の線は数えない）
  - きっかけが人でない流れ（タイマー・起動・OS からの通知など）は、「OS・タイマー」のような actor の箱を 1 つ置き、そこから線を引く（step は 1）
  - 同時に動くもの・順番が決まっていないもの（採点とひとことなど）は同じ step でよい
  - **同じ機能の箱は 1 つだけ描く**。もう一度その機能に戻るとき（結果を返す・続きを頼む）は、その箱へ戻る線を引く（例: 判断AI ⇢ 判定の司令塔「判断を返す」、判定の司令塔 ⇢ 受付窓口「判定結果を返す」）。戻る線は、後ろの段から前の段への矢印で描かれる
  - 1 つの箱へ 2 回頼む（前の結果を探して、最後にしまう）ときは、1 本の線にまとめて `label` に両方書く（「前の結果を探す・しまう」）
  - 結果を画面に描くのがブラウザ側のプログラムなら、出力の箱（判定結果の表示）をブラウザの列に置けばよく、入力の画面をもう一度描く必要はない
- **入力から最後の出力まで端折らずに描く**。図が「頼まれる側」へ潜ったところで終わらないようにする
  - 利用者などが最後に受け取るもの（画面に出る結果、通知、ダウンロードされるファイルなど）を `"output": true` の箱にする。置き場所は、受け取る場所の列（画面の表示ならブラウザの列）
  - 出力の箱は主な使い方ごとに置く。脇の入口（ログイン画面など）は、同じ場所に出る出力の箱を共有するか、説明に書くだけでよい。同じ場所に出る同じ種類の出力は 1 つの箱にまとめてよい
  - 結果が組み立てられた箱から最後の出力の箱まで、戻っていく道筋を `"kind": "result"` の線で結ぶ（例: 判定の司令塔 ⇢ 受付窓口「判定結果を返す」⇢ 判定結果の表示「格付けを表示する」）。最後の出力の箱へ入る線は result にする
  - さらに、最後の出力の箱から、それを受け取る人へ `"kind": "result"` の線（「格付けを見る」など）を引き、**流れを人のところで閉じる**（人は最初の段にいるので、戻る矢印になる）。人に届かない出力（外部システムへの送信など）は、受け取る先の箱へ結ぶ
  - 結果の線は主な道筋だけでよく、すべての呼び出しに戻りの線を付けない
- ルートを登録するだけの入口（`index.ts` `app.ts` など）は箱にしない。画面から各機能の箱へ直接線を引く。入口そのものに役割（共通の認証やエラー監視など）があるときだけ箱にする
- **グループ（groups）はプロダクトの実態で作る**。図では流れに沿った帯（横の流れでは横の帯、縦の流れでは縦の列）になる。「画面／サーバー／データ／外部サービス」のような決まった型を当てはめない
  - 単位は、コードで実際に分かれているもの: 動く場所（ブラウザ、Cloudflare Worker、バッチ…）、デプロイ単位、パッケージ、データの置き場所、外部サービス
  - 名前はそのプロダクトでの呼び方にする（「Cloudflare Worker」「判定パイプライン」）。数も実態どおりでよい
  - 書いた順に並ぶ（横の流れでは上から下、縦の流れでは左から右）。人 → 画面などの入口 → サーバー → 処理 → データ → 外部サービス のように、呼び出しが進む向きに並べる
- **外部サービスを使う箱には `service` を書く**（API・SaaS・マネージドな DB やストレージなど）。`name` は正式なサービス名（「Brave Search API」「Cloudflare D1」）、`provider` は提供元、`docs` は公式ドキュメントの URL（`curl -sIL` などで開けることを確かめられたときだけ。確かめられなければ省く）、`env` は必要な環境変数の**名前だけ**。箱には「◈ サービス名」が出て、右パネルとガイドに一覧が出る
- 計画と実装で**同じものには同じ id**。これが比較の鍵。計画だけ → `plan` のみ、計画外の実装 → `built` のみ
- `name` は日本語 2〜10 字（API・CSV のような略語は混ぜてよい。サービス名は `service` に書く）、`role` は箱に出るひとこと（24 字以内）、`detail` は専門用語を避けた 2〜3 文、`analogy` は身近なものへのたとえ 1 文。文体は「です・ます」
- `tech` は箱の中心になる技術を 1 つ、固有名詞のまま書く（Next.js など）。補助的なライブラリは `note` に書く。**同じ技術なら plan と built で同じ表記**にする（バージョン番号は書かない）。表記が違うと「技術を変えた（△変更）」と表示される
- `name` `role` `detail` `analogy` に専門用語を使ったら `glossary` に足す。`note` `issue` はなるべく平易に書きつつ、根拠としてファイル名・関数名・キー名は書いてよい
- 線は「頼む側 → 頼まれる側」。`label` は何を頼むかを短い動詞句で書く（「データを頼む」）。線は主な流れだけにし、本人確認のように多くの箱が使う共通の呼び出しは、代表する 1 本にまとめる
- 線は実際の呼び出しだけを引く。どこからも呼ばれていない機能（試作など）は線なしでよく、`note` にそう書く（「どの線ともつながっていません」の ⚠ は、事実ならそのままでよい）
- 利用者・管理者など人を表す箱は `"actor": true`（plan / built は書かない）。人は「使う人」などのグループにまとめて、最初のグループにする（図のいちばん端に出る）
- `built.progress` は 0〜1 の目安（完成なら省略。計画外の試作にも付けてよい）: 0.2 = 骨組みだけ / 0.5 = 主な部分の半分ほど / 0.8 = 動くが TODO が残る。`built.issue` はテスト失敗・動かないなど要注意のときだけ
- テストや実行で確かめず、コードを読んで判断した progress / issue は、`note` に「コードからの判断（未実行）」と書き、報告でもそう伝える
- **秘密は書かない**: API キー・パスワード・`.env` の値・個人情報。キー名やサービス名までにとどめる
- `project.updated` と `project.commit` は仕上げのスクリプトが自動で入れる

## 5. 仕上げ（毎回かならず実行）

```bash
node "${CLAUDE_SKILL_DIR}/scripts/archmap.mjs" docs/arch-map
```

- プロジェクトのルートで実行する（パスが空になっていたら `~/.claude/skills/arch-map/scripts/archmap.mjs`）
- ビューアの設置・更新、データの検証、整形、更新日と commit とログ日付の記入を行い、**arch-data.js を書き戻す**。このあと Edit するなら、直す箇所を Read し直してから
- `✕` が出たらその内容を直して再実行する。同じエラーが 2 回続いたら、データ全体を schema.md と見比べる
- `⚠` は表示はできるが、直せるものは直す（とくに説明の抜けと長すぎる文）
- 新規作成のときだけ `open docs/arch-map/index.html`（macOS。Linux は `xdg-open`）でブラウザを開く
