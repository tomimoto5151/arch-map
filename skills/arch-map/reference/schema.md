# arch-data.js の形式

ファイルの中身は `window.ARCH_MAP = { ... };` の 1 文（先頭のコメント行は仕上げのスクリプトが付けるので書かなくてよい）。`{ }` の中は厳密な JSON（コメント・末尾のカンマは不可）。
いろいろな状態をひと通り含む見本は、このスキルの `assets/example-data.js`（必要なときだけ読む）。

## 最小の例

React の画面・Express のサーバー・Supabase のデータベースでできた ToDo アプリ。グループ（図の列）は「このアプリで実際に分かれているもの」で作り、利用者の入力（step 1）から一覧が出るところ（step 5）まで、各機能が初めて動く順に描いている。

```js
window.ARCH_MAP = {
  "version": 2,
  "project": {"name": "ToDoアプリ", "summary": "やることを登録して、終わったら消せるWebアプリです。"},
  "groups": [
    {"id": "people", "name": "使う人", "color": "gray"},
    {"id": "browser", "name": "ブラウザ（React）", "desc": "画面", "color": "orange"},
    {"id": "server", "name": "Express サーバー", "desc": "注文を受ける本体", "color": "blue"},
    {"id": "supabase", "name": "Supabase", "desc": "借りているデータベース", "color": "green"}
  ],
  "nodes": [
    {"id": "visitor", "group": "people", "step": 1, "name": "利用者", "role": "ブラウザでやることを管理する",
     "detail": "やることを登録したり、終わったものに印を付けたりする人です。", "analogy": "メモ帳の持ち主です。", "actor": true},
    {"id": "web", "group": "browser", "step": 2, "name": "ToDo画面", "role": "やることの入力欄",
     "detail": "新しいやることを入力する画面です。保存はサーバーに頼みます。",
     "analogy": "冷蔵庫に貼ったメモです。",
     "plan": {"tech": "React"}, "built": {"tech": "React", "files": ["src/App.tsx"]}},
    {"id": "api", "group": "server", "step": 3, "name": "APIサーバー", "role": "画面からの注文を受ける",
     "detail": "画面から「保存して」と頼まれて、データベースに書き込み、新しい一覧を返します。",
     "analogy": "お店のレジ係です。",
     "plan": {"tech": "Express"}, "built": {"tech": "Express", "progress": 0.6, "files": ["server/index.js"]}},
    {"id": "db", "group": "supabase", "step": 4, "name": "データベース", "role": "やることを保存する",
     "detail": "登録されたやることを、アプリを止めても消えないようにしまっておきます。",
     "analogy": "書類をしまう引き出しです。",
     "service": {"name": "Supabase", "provider": "Supabase", "docs": "https://supabase.com/docs", "env": ["SUPABASE_URL", "SUPABASE_ANON_KEY"]},
     "plan": {"tech": "Supabase（PostgreSQL）"}},
    {"id": "list", "group": "browser", "step": 5, "name": "やること一覧", "role": "保存されたやることが並ぶ", "output": true,
     "detail": "サーバーから返ってきたやることが、新しい順に画面に並びます。利用者が最後に目にするものです。",
     "analogy": "冷蔵庫に貼り直されたメモの束です。",
     "plan": {"tech": "React"}, "built": {"tech": "React", "files": ["src/TodoList.tsx"]}}
  ],
  "edges": [
    {"from": "visitor", "to": "web", "label": "やることを入力する"},
    {"from": "web", "to": "api", "label": "保存を頼む"},
    {"from": "api", "to": "db", "label": "書き込む"},
    {"from": "db", "to": "api", "label": "新しい一覧を返す", "kind": "result"},
    {"from": "api", "to": "list", "label": "一覧を描いてもらう", "kind": "result"},
    {"from": "list", "to": "visitor", "label": "一覧を見る", "kind": "result"}
  ],
  "glossary": [{"term": "API", "desc": "画面とサーバーがやりとりするための注文の受付窓口です。"}],
  "log": [{"date": "2026-10-03", "view": "both", "text": "図を新しく作成"}]
};
```

箱は機能ごとに 1 つだけ置く。`db` から `api`、`list` から `visitor` への線のように、前の段の機能にもう一度戻るところは、戻る矢印で描かれる（`api` や `visitor` をもう一度描かない）。

## 項目

### project（必須）
- `name` プロジェクト名（必須）
- `summary` アプリ全体をひとことで。初心者が最初に読む 1〜2 文
- `updated` `commit` 仕上げのスクリプトが自動で書く（手で書かなくてよい）

### groups（必須） — 図の列（横の流れでは縦の列、縦の流れでは横の帯）。プロダクトの実態どおりのまとまり
- `id` 英小文字・数字・`-` `_`
- `name` そのプロダクトでの呼び方（「Cloudflare Worker」「判定パイプライン」）、`desc` ひとことの説明
- `color` `orange` `blue` `green` `purple` `cyan` `pink` `gray` のどれか
- 書いた順に並ぶ（横の流れでは左から右、縦の流れでは上から下）。人 → 画面などの入口 → サーバー → 処理 → データ → 外部サービス のように、呼び出しが進む向きに並べる
- `tool` 実装用の道具（ビルド、データ準備、評価・調整、確認用 CLI など、本番のサービスの中では動かないもの）のグループなら `true`。流れの図の後ろ（横の流れなら右端、縦の流れなら下）の「⚒ 実装用の道具」の区画に描かれ、中の箱に `step` は要らない

まとまりの作り方:

- ❌ どのアプリにも当てはまる型を当てはめる: 「利用者 / 画面 / サーバー / データ / 外部サービス」
- ❌ 開発・テスト用の道具（評価スクリプト、確認用 CLI、ローカル用サーバー、ビルド）を、本番の部品と同じ列に混ぜる → `"tool": true` のグループに分ける（アプリ自体が CLI ツールや開発者向けの製品なら、それは本番の部品）
- ❌ 開発者を人の箱として描く
- ✅ コードで実際に分かれているもので作る: 動く場所、デプロイ単位、パッケージ、データの置き場所、外部サービス

| こういうプロダクトなら | 列の例（左から） |
| --- | --- |
| Next.js を Vercel で動かす | 使う人 ／ ブラウザ ／ Vercel（Next.js サーバー） ／ データベース ／ 借りているサービス |
| Cloudflare で動かす | 使う人 ／ ブラウザ ／ Cloudflare Worker ／ 判定パイプライン ／ Cloudflare D1 ／ 外部 API |
| モノレポ | 使う人 ／ `apps/web` ／ `apps/api` ／ `packages/shared` など、実際のパッケージ名 |
| スマホアプリ | 使う人 ／ iOS アプリ ／ バックエンド ／ プッシュ通知などの外部サービス |
| CLI ツール（それ自体が製品） | 使う人 ／ コマンド本体 ／ 設定ファイル・キャッシュ ／ 呼び出す外部 API |

### nodes（必須） — 箱
- `id` 英小文字・数字・`-` `_`。**計画と実装で同じものは同じ id**
- `group` 所属するグループ（列）の id
- `step` その機能が初めて動く順番（1 から。1 つの整数）。列の中はこの順に上から（縦の流れでは帯の中を左から）詰めて並び、箱の左上に番号が出る。同じ箱は 1 回だけ置き、もう一度その機能に戻るところは戻る線で描く。同時に起きることは同じ step でよい
- `name` 日本語 2〜10 字（箱の見出し）。API・CSV のような略語は混ぜてよい。サービス名は `service` に書く
- `role` 箱に出るひとこと（24 字以内）
- `detail` くわしい説明。専門用語を避けて 2〜3 文、です・ます調
- `analogy` 身近なものへのたとえ 1 文（「お店の受付係です。」）
- `actor` 人を表す箱なら `true`（このときは plan / built を書かない）
- `output` 利用者などが**最後に受け取るもの**（画面に出る結果、ターミナル出力、レポート、ファイル、通知など）なら `true`。箱に「⇥ 最後の出力」が出る。主な使い方ごとに置き、受け取る人（actor）や先の箱へ `kind: "result"` の線で結ぶ
- `service` 外部サービス（API・SaaS・マネージドな DB やストレージなど）を使う箱なら書く。箱に「◈ サービス名」が出る
  - `name` 正式なサービス名（必須。「Brave Search API」「Cloudflare D1」）
  - `provider` 提供元（「Brave」「Cloudflare」）
  - `docs` 公式ドキュメントの URL（`https://` で始まる。実在を確かめられたときだけ）
  - `env` 必要な環境変数の**名前だけ**（`["BRAVE_API_KEY"]`）。値は絶対に書かない
- `plan` 計画にある箱なら書く。中身がなければ `{}`
  - `tech` 予定している技術、`note` 計画のメモ（計画書に明記がなく推測で置いた箱なら、そう書く）
- `built` 実装済み・作業中の箱なら書く。中身がなければ `{}`
  - `tech` 実際に使っている技術。計画と同じ技術なら plan と**同じ表記**（バージョン番号は書かない）
  - `note` 実装のメモ。progress や issue の根拠もここに書く
  - `progress` 0〜1 の進み具合の目安（完成なら省略）。0.2 = 骨組みだけ / 0.5 = 主な部分の半分ほど / 0.8 = 動くが TODO が残る
  - `files` 関係する主なファイル（3 つ程度まで、プロジェクトルートからの相対パス）
  - `issue` テスト失敗・動かないなど、要注意のときだけ（箱が赤く光る）

比較タブでの表示:

| plan | built | 表示 |
| --- | --- | --- |
| あり | あり | 完成（progress が 1 未満なら作業中）。tech の文字列が違えば「△変更」 |
| あり | なし | 未着手（点線） |
| なし | あり | 計画外（黄色） |

### edges — 線（頼む側 → 頼まれる側）
- `from` `to` 箱の id
- `label` 何を頼むか。短い動詞句（「データを頼む」「写真を保存する」）
- `kind` 結果が返っていく・出力される流れなら `"result"`（点線と白抜きの矢印で描かれる）。省略すると「頼む」線。結果が組み立てられた箱から最後の出力の箱を通って、受け取る人まで。主な道筋だけに付ける
- `only` 片方の図だけに出す線なら `"plan"` か `"built"`（省略すると、両端の箱がある図すべてに出る。計画だけの箱への線に `only` は要らない）
- 線はふつう前の step から後の step へ。もう一度前の機能に戻るところ（結果を返す・続きを頼む）は、後ろの step から前の step への線にする（戻る矢印で描かれる）
- 同じ step の箱どうし・同じグループの箱どうしの線も引ける（同じ列の中なら、右へふくらんで折り返す線で描かれる）

### glossary — 用語ミニ辞典（右パネルに出る）
- `{"term": "API", "desc": "..."}`。`name` `role` `detail` `analogy` に出てくる専門用語を 3〜10 個

### log — 更新ログ（右パネルのガイドに新しい順で出る）
- `{"date": "YYYY-MM-DD", "view": "plan" | "built" | "both", "text": "何が変わったか"}`。`date` を省略するとスクリプトが今日の日付を入れる
- 末尾に追加していく。30 件を超えると古いものからスクリプトが消す

### 旧形式について
`"version": 1` の `layers` / `layer` で書かれたデータは、仕上げのスクリプトが自動で `groups` / `group`（version 2）に書き換える。
`step` のない箱は、列の中で書いた順に（step のある箱の後ろに）並び、番号は出ない。グループの `row` / `cols`（古い段の図の並べ方）は今のビューアでは使われない。新しく書くときは `step` を使う。
`step` が配列（同じ箱を複数の段に置く古い形式）のデータは、仕上げのスクリプトが最初の段だけに直す。
